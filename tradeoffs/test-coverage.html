Test coverage: confidence vs. cost

The first tests catch the most bugs for the least effort. Each extra percent of coverage costs more and catches less, and even 100% coverage doesn't mean the code is right. How far to go depends on what an escaped bug costs.

Bugs caughtvs.Testing effort

The trade-off

Code coverage measures how much of the code runs during the tests. Raising it catches bugs before users see them, but the returns fall off. The first tests exercise the main paths, where most bugs live. Later tests chase error handling, odd branches and code that is awkward to reach, and they cost more to write and to keep up to date every time the code changes.

Coverage is also only a proxy. A line can run during a test without any assertion checking that it did the right thing, so 100% coverage still lets bugs through. Google's testing guidance treats about 60% as acceptable, 75% as commendable and 90% as exemplary, and warns against fixed targets for every project. The right level depends on the cost of an escaped bug: a payments system and a weekend prototype should not have the same target.

How to use it

  1. Test the risky parts first. Core business logic, money, security and anything that has broken before.
  2. Use coverage to find gaps, not as a score. Look at which important code isn't tested, rather than at the overall percentage.
  3. Check test quality too. Mutation testing (deliberately breaking the code to see if tests fail) shows whether tests actually check anything.
  4. Set the bar per component. Stricter for critical paths, looser for glue code and experiments.

Example

A team was told to reach 90% coverage across every service. Developers wrote tests for getters and configuration code to hit the number, while the billing module stayed at 70% because its edge cases were hard to set up. After a billing incident, the team dropped the global target, required 90% only for billing and authentication, and used the freed time to add mutation testing there.

Watch out for

  • The curves here are a toy model. How fast returns fall depends on the code and on how good the tests are.
  • Goodhart's law. Once coverage becomes a target, people write tests to raise it rather than to find bugs.
  • Brittle tests. Tests that check implementation details break on every refactor, which adds cost without catching real bugs.
  • Related: chasing a metric instead of the goal is proxy metrics vs. the real goal, the same U-shaped cost is in prevention vs. failure, and skipping tests to go faster is technical debt.
