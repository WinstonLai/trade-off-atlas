The trade-off

"Don't repeat yourself" (DRY) is one of the first rules programmers learn: if the same logic appears in several places, extract it so a change is made once. When the copies really do change together, this is a clear win. Every shared fix is one edit instead of several, and nobody forgets one of the copies.

The trouble starts when code that looks the same serves needs that later diverge. Each new special case gets a parameter or a flag, each change has to work for every caller, and the shared function becomes the hardest code in the system to touch. Sandi Metz summed this up as "duplication is far cheaper than the wrong abstraction". So the decision isn't "is this repeated?" but "will these pieces change for the same reasons?" Many teams follow the rule of three: tolerate one duplicate, and abstract when a third copy shows what is really shared.

How to use it

  1. Ask why the code changes. If two copies change for the same business reason, share them. If they only look alike, they may be coincidentally similar.
  2. Wait for the third case. Two examples rarely show which parts are truly common.
  3. Watch for flags. Boolean parameters that switch behaviour per caller are a sign that an abstraction is serving too many masters.
  4. Be willing to inline it again. Copying a bad abstraction back into each caller, then simplifying each copy, is a legitimate refactoring.

Example

Three services formatted invoices with nearly identical code, so a developer merged them into one shared library. A year later, one service needed tax rules for a new country, another needed a different currency format, and the third needed a legal footer. The library grew twelve options, and every release needed sign-off from all three teams. The teams eventually copied the code back and each deleted the options it didn't use, which left three short, simple formatters.

Watch out for

  • The numbers here come from a toy model. Real effort depends on how big the code is and how well the abstraction was designed.
  • Duplicated bugs. Copies don't just share features: a bug in one is probably in all of them. Security-critical logic is usually worth sharing even when it's awkward.
  • Sunk cost. The longer an abstraction has existed, the harder it feels to undo. That isn't a reason to keep it.
