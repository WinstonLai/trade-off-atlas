The trade-off

Every compression codec trades CPU for bytes. Fast codecs like LZ4 and Snappy roughly halve typical data while barely touching the CPU. Zstandard (Zstd) at low levels compresses noticeably better for a small extra cost. High levels of Zstd, and older codecs like gzip, squeeze out more, but compression can be tens or hundreds of times slower. Decompression is usually much faster than compression, though gzip is slow at both.

Whether the extra squeeze pays off depends on the rest of the pipeline. If the bottleneck is the network or disk, fewer bytes means less waiting, and the saving is repeated every time the data is read. If the storage is fast local SSD and the data is read once, any compression can cost more time than it saves, though it still saves storage. That is why columnar formats such as Parquet commonly default to Snappy or Zstd at low levels, and why archives use the highest levels: written once, stored for years, read rarely.

How to use it

  1. Find the bottleneck. If jobs are waiting on I/O, compress harder. If they're CPU-bound, compress less.
  2. Count the reads. Data that is written once and read many times justifies a slower, stronger codec.
  3. Separate hot and cold data. Fast codecs for data being actively processed, strong ones for archives.
  4. Benchmark on your own data. Ratios vary hugely: logs and JSON compress well, images and already-compressed files barely at all.

Example

A data team stored its event tables as gzip-compressed JSON. Queries were slow because every read decompressed the files on a single core. Moving to Parquet with Zstd at level 3 made the files slightly smaller and queries several times faster. For the seven-year compliance archive, which is almost never read, they used Zstd at its highest level, which cut the storage bill by a further fifth.

Watch out for

  • The numbers here are illustrative. Codec speeds and ratios depend on the data, the hardware and the library version. Measure before you switch.
  • Splittability. A single large gzip file can't be read in parallel. Formats like Parquet compress in blocks so many workers can read one file.
  • Cost isn't only time. Cloud storage and network egress are billed by the byte, so a better ratio can pay for itself even when it's slower.
  • Related: storage layout is row vs. column storage, file layout is many small vs. few large files, and spending CPU to save storage, or the reverse, is time vs. space.
